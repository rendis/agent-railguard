# Develop Go Hexagonal Service

## Close one verified delivery

1. **Route.** Read governing instructions and any active specification or handoff, then [change-routing.md](references/change-routing.md). Use this workflow for production behavior, architectural or runtime boundaries, or explicitly requested complete delivery. Standalone test, E2E, configuration, and read-only review work remain with their focused workflows; documentation-only and explanation-only requests need no delivery workflow unless they require production or cross-boundary edits. Declare authority, owner, affected boundary, and focused inner skills. Assess adopted quality readiness before relying on its gates. Complete when routing and configuration state are explicit.
2. **Discover.** Read [implementation-analysis.md](references/implementation-analysis.md) and the shared [design lens](references/design-lens.md). Search behavior, tests, consumers, dependencies, configured capabilities, current library types, public contracts, persistence, and baseline failures. Classify the request as verify, extend, reuse, extract, replace, or create. Produce observed consumers, existing capability, ownership boundary, deterministic transformations and effects, simplest end-to-end slice, compatibility evidence, debt class, and a falsifiable test strategy. Complete before editing; stop when the request is already satisfied.
3. **Contract.** Read [architecture-contract.md](references/architecture-contract.md) for crossed boundaries, [go-design-practices.md](references/go-design-practices.md) before Go changes, [REST stack selection](references/rest-stack-selection.md) before selecting or changing an inbound or outbound HTTP stack, [runtime configuration](references/runtime-configuration.md) when configuration is created or changed, and [error-management.md](references/error-management.md) when error contracts change. Trace actor → entry → application → external capability → composition. Present options when the REST selection workflow or observed compatibility, data, architecture, migration, external consumers, or cost requires a user decision. Otherwise choose the simplest durable direct solution, replace internal obsolete paths atomically, and add no fallback, alias, speculative abstraction, or ceremony.
4. **Develop.** For a feature, fix, or behavior-preserving refactor, load the `tdd` skill. Load the `design-tests` skill once only when a proof is created or materially redesigned, and reuse it across TDD, Go testing, and E2E. Use focused Go level/style references without loading full hardening for each slice. Features and fixes need discriminating RED→GREEN; refactors need a green safety net and must not manufacture RED. Implement the smallest working vertical slice, refactor while green, and repeat until the behavior contract closes.
5. **Accept.** Load the `build-e2e-test-suite` skill when a public journey, runtime boundary, or canonical acceptance gate applies. Assign a functional failure to the smallest behavioral owner and run another focused TDD cycle; form a new candidate and rerun the affected journey. Setup, dependency, readiness, timeout, or cleanup inability is `BLOCKED_SETUP`, preserves diagnostics, and is neither product failure nor pass. Load `test-go-service` for test-only work; configuration-only and non-executable edits use proportionate evidence.
6. **Candidate.** Read [verification.md](references/verification.md). Run the repository-native standard gate with exact pins and configs. Route each failure to behavior, tests, E2E, or configuration without weakening thresholds, exclusions, assertions, or source merely to satisfy a metric. Repeat affected focused signals and the standard command after governed edits. Complete with a green fixed snapshot or an honest blocked prerequisite.
7. **Challenge.** Load the `review-go-quality` skill read-only over that fixed snapshot. Challenge request alignment, correctness, simplicity, semantic reuse, effect isolation, current need for patterns, compatibility, debt scope, naming, documentation, and test sensitivity. This workflow remediates an accepted finding and creates a new candidate; the previous review cannot follow an edit.
8. **Harden.** Load `test-go-service` for risk- or policy-selected integration, contract, fuzz, race, benchmark, mutation, flakiness, or test-code signals. Run every applicable native gate and classify noisy evidence by stable verdict rather than byte identity. `configure-go-quality` owns missing reproducibility inputs; the behavioral owner handles product findings. A hardening edit starts candidate and review again.
9. **Deliver.** Run affected signals and the final canonical command, inspect the diff, and report discovery, design lens, compatibility, debt, TDD or refactor evidence, E2E classification, configuration state, review, hardening, commands, results, and unobserved dimensions. Complete only when [verification.md](references/verification.md) is satisfied.

Keep skill coordination shallow and idempotent: this skill owns delivery, each specialized skill owns one phase, and shared test-design or configuration assessments are loaded once per behavioral contract or snapshot. Do not create cycles, duplicate loads, legacy bridges, or a second quality framework.
