# Configure Go Quality

## AI Harness ownership contract

Inspect `Makefile` for `# ai-harness:managed:start id="verification.go-quality"` before proposing writes. When present, treat `make check` and `make verify` as the installed canonical surface and run them directly for the adopted scope. Express any missing or stronger quality surface as desired configuration for `verification-profile:go-quality`; only an AI Harness `Resolve -> Plan -> Review -> Apply` operation may regenerate that block. If the profile is absent, classify Assess as `MISSING`; in Apply or Repair, request that profile through the available AI Harness selection route and stop as `MISSING` when no supported route can materialize it. Keep Git gates optional: using or configuring this skill never activates `pre-commit` or `pre-push` implicitly.

## Deterministic return invariant

The readiness classifier is the only owner of the final configuration state. Run it as the last classification action and copy its `state` and `status` fields unchanged into prose and structured output. Before returning, compare both fields mechanically; a mismatch, including reporting `ready_with_findings` when the classifier emitted `blocked_setup`, is an incomplete result and must not be delivered.

## Establish configuration readiness

1. **Authority.** Declare `Assess`, `Apply`, or `Repair` and the adopted signals. `Assess` never writes. `Apply` and `Repair` reuse an already active `develop-go-hexagonal-service` workflow; do not load it recursively. When this skill is loaded during a review, use only `Assess` over the fixed snapshot. Complete when authority, owner, scope, and requested signals are explicit.
2. **Assess.** Read [configuration-lifecycle.md](references/configuration-lifecycle.md). Inspect the module or workspace, Go version, pins, native configurations, task and CI owners, explicit scopes, ignore policy, home inheritance, and prerequisites. Run the readiness probes without changing governed files. Complete with exactly one state: `READY`, `READY_WITH_FINDINGS`, `MISSING`, `BROKEN`, or `BLOCKED_SETUP`.
3. **Select.** Read [quality-profiles.md](references/quality-profiles.md) and [deterministic-gate.md](references/deterministic-gate.md). Adopt only signals with a named defect class, scope, cost, decision rule, owner, and local or CI consumer. Preserve a stronger valid repository policy; do not weaken thresholds, add exclusions, or enable tools merely to obtain a green baseline. When a generic request applies to a Go service with no stronger policy, read [default-go-service-profile.md](references/default-go-service-profile.md) and adopt its pins, native configs, task surface, ignores, and readiness probes as one baseline. Omit a signal only with explicit non-applicability evidence; do not select an arbitrary subset or discover versions from the network.
4. **Materialize.** In `Apply` or `Repair`, read [tool-policy.md](references/tool-policy.md). Change only reproducibility inputs: exact Go/tool pins, native tool configuration, repository-native task or CI commands, declared source scopes, execution documentation, and generated-evidence ignores. Materialize an approved multi-tool baseline as one module transaction and reject a partial tool set; dependency failure cannot turn an absent repository pin into `BLOCKED_SETUP`. Preserve the existing task and CI owner. When AI Harness owns the verification block, submit semantic scopes and required targets to its desired state and review the regenerated plan; a direct edit to the marked block is an invalid candidate. Never add a repository-local quality application, private policy schema, runner source, attestation, disposition ledger, report reader, compatibility bridge, alias, or command that reaches an installed skill path. Do not edit production code, tests, E2E behavior, assertions, thresholds, or exclusions to remediate product findings.
5. **Prove.** Validate schemas and effective configuration with native parser-only commands where the pinned tool provides them, resolve every pin from the repository, exercise changed commands, prove home isolation and ignored output paths, run the isolated negative probe, and compare local and CI entrypoints. A version command proves only pin resolution. When a tool has no parser-only validator, prove its explicit config path and command structurally, then use its first real direct execution as the authoritative config/runtime proof. Require every adopted direct target and aggregate to resolve, then execute each real canonical dimension exactly once for classification; do not add a redundant engine dry-run. Keep the wiring/readiness target separate from product gates: evidence may combine a successful readiness probe with independently observed canonical executions. A second `Apply` over a materialized state must produce no diff and the same state. Preserve product failures and blocked prerequisites without remediation. After classifying each cause, run `scripts/classify-readiness.py` from this installed skill with `--inputs ready|missing|broken`, one `--blocked-prerequisite` per unavailable required cause, and one `--product-finding` per executed product failure. Its JSON result is authoritative; do not choose precedence or translate state manually.
6. **Return.** Report mode, the exact `state` emitted by `scripts/classify-readiness.py`, snapshot, adopted signals, changed or proposed inputs, versions, scopes, commands, exit codes, negative-probe result, parity, and every blocked prerequisite. Account for each baseline dimension as passed, product finding, blocked prerequisite, or non-applicable with observed evidence; silently absent race, fuzz, vulnerability, mutation, or E2E is incomplete. When the caller provides a structured status field, copy its `status` field without translation. The prose state and structured status must come from the same JSON result; do not substitute a generic completion or a weaker state. Quote the final classifier JSON in evidence, then verify the structured status equals that JSON before sending the response. Classify product remediation under `develop-go-hexagonal-service`, test sensitivity under `test-go-service`, E2E behavior under `build-e2e-test-suite`, and contextual findings under `review-go-quality`.

## Default-profile completeness proof

Before classifying the default profile, require `make -n test-race test-fuzz` to resolve and inspect the expanded `make -n verify-hardening` graph for both `-race` and `-fuzz`. An absent capability is `MISSING` or `BROKEN`, never `READY_WITH_FINDINGS`; do not infer completeness from the aggregate target name.

## Composition contract

- A valid pinned canonical gate is consumed directly; do not load this skill merely to rerun it.
- Resolve one assessment per snapshot and reuse it until pins, configuration, scopes, task commands, CI, or authority change.
- `Repair` restores reproducibility inputs only. A product failure is not broken configuration.
- Stop at the first preserved product diagnostic. Never edit product, tests, E2E, assertions, or fixtures in order to make an Apply or Repair candidate pass; such an edit invalidates the configuration result.
- Replace obsolete configuration atomically. Do not preserve legacy commands or artifacts without an observed external contract.
- Configuration proves that signals can execute reproducibly; it does not prove semantic correctness, naming clarity, useful documentation, architecture, or test sensitivity.
